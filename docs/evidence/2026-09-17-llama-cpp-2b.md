# llama.cpp + MiniCPM5-2B smoke record

Date: **2026-09-17**. Status: **verified reference backend for v0.4.0; not a benchmark score.**

This record covers what changed in 0.4.0: the reference backend moved from SGLang (MiniCPM5-1B on
port 30000) to `llama-server` serving MiniCPM5-2B on port 8080. It establishes that the request
shape the runtime sends is accepted by llama.cpp and that the default token budget is wrong for a
2B thinking chain. It does **not** establish diagnostic accuracy or run-to-run stability — that is
what [the benchmark plan](../benchmark-plan.md) covers.

## Environment

| Item | Value |
|---|---|
| Model artifact | `~/models/MiniCPM5-2B-Q4_K_M.gguf` (symlink into an Ollama blob store) |
| Runtime | `/opt/homebrew/bin/llama-server` b10150 (`dee2a846b`), AppleClang 21.0.0, Darwin arm64 |
| Host | macOS, Apple Silicon, `-ngl 99` (full GPU offload) |
| Context | `-c 65536`, `-ctk q8_0`, `-ctv q8_0`, `--parallel 1` |
| Endpoint | `http://127.0.0.1:8080/v1` |
| Served model id | `minicpm5-2b` (from `--alias`), `n_ctx` reported as 65536 |
| Launch method | `~/bin/llamactl` behind `~/Desktop/llama服务器.command`; launchd label `com.caciniep.llama-server-minicpm5`, `RunAtLoad`/`KeepAlive` disabled |

Start/stop is manual on purpose: a `KeepAlive` job would hold roughly the model footprint resident
across reboots. The wrapper also unloads models pinned in Ollama by `keep_alive:-1`, which was a
separate source of unexplained memory use.

## Request compatibility

The runtime sends `tool_choice`, `chat_template_kwargs.enable_thinking`, and
`reasoning_effort` on every turn. All three were probed directly against `b10150`:

| Probe | Result |
|---|---|
| `/v1/models` | `id=minicpm5-2b`, `n_ctx=65536` |
| `tool_choice="required"` + `chat_template_kwargs` + `reasoning_effort="none"` | HTTP 200, `finish=tool_calls`, correct `resolve_dns` call |
| `tool_choice="auto"` + `reasoning_effort="none"` | HTTP 200 |
| `tool_choice="required"` alone | HTTP 200, `finish=tool_calls` |
| `enable_thinking=true` + `reasoning_effort="high"` | HTTP 200, `finish=tool_calls`, 470 chars of reasoning |

So **none of the compatibility fallbacks in `agent._create_with_fallback` fire** on this runtime. They
remain necessary for other backends.

One behaviour worth recording: with `chat_template_kwargs` omitted, the model emitted 75 characters
into `reasoning_content` even when thinking was meant to be off. The flag is load-bearing, not
documentation.

## The token-budget problem

Prompt: `npm install times out fetching registry.npmjs.org on macOS. DNS works in browser but
terminal fails.`, with the real system prompt and real tool results replayed per turn, thinking
enabled.

| Turn | `max_tokens` | `reasoning_content` chars | `finish_reason` | Outcome |
|---|---|---|---|---|
| 1 | 2048 | 1152 | `tool_calls` | ok |
| 2 | 2048 | 2736 | `tool_calls` | ok |
| 3 | 2048 | 8288 | `length` | **truncated — no tool call, no answer** |
| 3 | 4096 | 5241 | `tool_calls` | ok |
| 3 | 8192 | 25560 | `tool_calls` | ok |

The chain-of-thought length varies by more than an order of magnitude (1.1k–25.5k characters), so no
single fixed budget is safe. What made this dangerous rather than merely lossy is what a truncated
turn looks like on the wire:

```
finish_reason=length, reasoning_content=8288 chars, content=0 chars, tool_calls=[]
```

llama.cpp writes the cut-off chain of thought to `reasoning_content` and leaves `content` empty. The
agent only inspected `message.content`, so it raised
`NetworkDoctorError("MiniCPM5 returned neither text nor tool calls")` and threw away every tool
result gathered so far. The truncated text itself was the model bookkeeping its own tool calls
(*"I've used: 1. resolve_dns ... That's 4. I can't"*), which is a useful hint that the guardrail
prompt is costing real budget.

0.4.0 changes both halves: `--max-tokens` (default 2048, 8192 under `--thinking`) and a truncated
turn now yields `model_response_truncated_by_budget` plus a partial diagnosis carrying the evidence.
A truncated *first* turn still raises `StepLimitError`, because there is nothing to preserve.

## End-to-end runs

Non-thinking, default flags:

```
minicpm-network-doctor --progress "npm install times out fetching registry.npmjs.org on macOS..."
```

Four tools ran (`resolve_dns`, `inspect_hosts_file`, `inspect_proxy_environment`, `test_tcp`,
`test_http`), all four required sections were present, and the fake-IP address `198.18.0.52` was
correctly classified as a proxy-managed DNS path rather than declared a DNS failure. `--check-server`
reports `Server reachable: http://127.0.0.1:8080/v1`, `Connection: direct`, `Models: minicpm5-2b`.

Thinking mode also required the timeout default to rise from 180s to 600s: with `--max-tokens 8192`
a single run exceeded 180s on one turn after four turns of successful tool calls.

### Thinking mode still did not converge — and that is the point

The same symptom under `--thinking` (default 8192 budget, 600s timeout) ran four turns of
successful tool calls, then hit truncation on a later turn. With the fix in place the run ended:

```
warnings: model_response_truncated_by_budget
Diagnosis: The model did not converge on a final diagnosis (the model exhausted its token budget
while reasoning; raise --max-tokens to give it room to finish).
Evidence:
- resolve_dns (registry.npmjs.org) -> addresses=198.18.0.52 (fake-ip (198.18.0.0/15))
- test_tcp (registry.npmjs.org) -> ok
- inspect_proxy_environment -> proxy_variables={...}
- inspect_hosts_file (registry.npmjs.org) -> overridden=False
```

Status `partial`, all four tool events retained, exit code 0. Before 0.4.0 the identical situation
produced `error: MiniCPM5 returned neither text nor tool calls` with exit code 1 and **zero**
evidence.

**8192 is not sufficient to make 2B thinking converge reliably**, and raising the default further
is not the right answer: it lengthens every turn and pushes against the 600s timeout ceiling. The
defensible position is that `--max-tokens` is a knob the user owns, and that failing to converge is
now non-destructive. If thinking needs to be dependable on this model, the fix is a stronger model,
not a bigger fixed budget.

## What this record does not establish

- **Diagnostic accuracy.** One symptom, one run. No scenario suite, no repetitions.
- **Stability.** Thinking-mode chain length varied enough that a different prompt could still
  truncate at 8192; that is why `--max-tokens` is exposed rather than hardcoded.
- **Quantization margin.** Q4_K_M worked here. That does not bound Q3 or lower, and it does not
  transfer to other runtimes — the previous F16 guidance came from Ollama and SGLang behaviour.
- **Non-Apple-Silicon behaviour.** `-ngl 99` full offload on a different device class may change both
  timing and tool-call reliability.
- **Thinking convergence.** Under `--thinking`, MiniCPM5-2B truncated again at the 8192 default on a
  multi-turn run. The evidence survived, but no diagnosis was produced. `--thinking` should be read
  as "try harder, may still not finish", not as a mode that reliably converges on this model.
